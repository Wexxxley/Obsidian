## **Módulo 1: Arquitetura e Runtime Environment**

O Node.js é um ambiente de execução (_runtime_) JavaScript construído sobre a engine V8 do Google Chrome. Ele permite a execução de código JavaScript fora do navegador (server-side). Ao contrário de plataformas baseadas em _threads_ concorrentes (como Apache/PHP ou servidores Java tradicionais), o Node.js opera sob um modelo de **I/O não bloqueante e orientado a eventos**.

A arquitetura do Node.js é composta por três camadas principais:

### **1. Engine V8 (Google)**

É a biblioteca C++ responsável por executar o código JavaScript.

- **JIT (Just-In-Time) Compilation:** O V8 compila código JavaScript diretamente para código de máquina (nativo) antes de executá-lo, em vez de usar um interpretador tradicional.
    
- **Memory Heap & Call Stack:** O V8 gerencia a alocação de memória e a pilha de chamadas (Call Stack), onde as funções são empilhadas e executadas.
    

### **2. Libuv**

Esta é uma biblioteca C multiplataforma que fornece suporte a operações de I/O assíncronas baseadas em eventos. Ela é o "motor" por trás do modelo não bloqueante do Node.js.

- **Event Loop:** Implementado pela Libuv.
    
- **Thread Pool:** Embora o JavaScript seja _single-threaded_ (executado em uma única thread principal), a Libuv mantém um _pool_ de threads (padrão: 4 threads) para executar operações pesadas de sistema operacional (como leitura de arquivos, DNS lookup, compressão) que não podem ser tratadas de forma não bloqueante pelo kernel do SO.
    

### **3. Node.js Bindings (Node API)**

Esta camada conecta o código JavaScript às bibliotecas C/C++ (V8 e Libuv). Quando você chama `fs.readFile` em JavaScript, os _bindings_ traduzem essa chamada para a função C++ correspondente na Libuv.

### **O Event Loop e o Modelo Single-Threaded**

É crucial entender que o Node.js é **Single-Threaded** no que tange a execução do código JavaScript do usuário e o Event Loop. Isso significa que apenas uma instrução JavaScript é executada por vez na thread principal.

No entanto, o Node.js é **concorrente** através do Event Loop.

#### **Fases do Event Loop**

Quando o Node.js inicia, ele inicializa o Event Loop, processa o script de entrada e entra em um loop de fases. Cada fase possui uma fila FIFO de callbacks a serem executados:

1. **Timers:** Executa callbacks agendados por `setTimeout()` e `setInterval()`.
    
2. **Pending Callbacks:** Executa callbacks de I/O adiados para a próxima iteração.
    
3. **Idle, Prepare:** Uso interno apenas.
    
4. **Poll:** Recupera novos eventos de I/O; executa I/O related callbacks. O Node pode bloquear aqui se não houver timers pendentes.
    
5. **Check:** Executa callbacks agendados por `setImmediate()`.
    
6. **Close Callbacks:** Executa callbacks de fechamento (ex: `socket.on('close', ...)`).
    

> **Nota Técnica:** O processamento pesado na thread principal (ex: um loop `for` de 1 bilhão de iterações ou processamento de imagem em JS puro) bloqueará o Event Loop. Isso impede que o Node processe novas requisições ou execute callbacks de I/O, paralisando a aplicação. Isso é conhecido como _Event Loop Blocking_.
