

### 1. Mecanismos de Armazenamento Client-Side 

Os navegadores modernos oferecem diferentes APIs para armazenamento de dados no lado do cliente. Cada uma possui escopos, limites e propósitos estritos.

- **Web Storage API (localStorage):**
    
      
    - **Definição:** É um mecanismo que permite o armazenamento de dados no formato chave-valor diretamente no navegador.
        
          
        
    - **Persistência:** Possui persistência contínua. Os dados não expiram com o tempo e permanecem no dispositivo até que sejam explicitamente deletados via código JavaScript ou pela limpeza de dados de navegação realizada pelo usuário.
        
          
        
    - **Capacidade:** Tipicamente restrita a limites entre 5 MB e 10 MB por origem, dependendo da implementação do navegador.
        
          
        
    - **Formato dos Dados:** Armazena exclusivamente dados do tipo _String_. Objetos complexos devem ser serializados (por exemplo, via formato JSON) antes da gravação.
        
          
        
    - **Acessibilidade e Segurança:** Os dados são acessíveis por qualquer script que execute na mesma origem. Não há proteção nativa contra leitura por scripts maliciosos injetados na página.
        
          
        
- **Web Storage API (sessionStorage):**
    
      
    - **Definição:** Possui a exata mesma interface de programação do _localStorage_, porém com um ciclo de vida restrito.
        
          
        
    - **Persistência:** Os dados são mantidos apenas enquanto a sessão da página (a aba ou janela específica do navegador) estiver aberta. O fechamento da aba destrói os dados permanentemente.
        
          
        
- **IndexedDB:**
    
      
    - **Definição:** É um sistema de gerenciamento de banco de dados não relacional (NoSQL) embutido no navegador, projetado para armazenar grandes volumes de dados estruturados.
        
          
        
    - **Características:** Suporta transações, índices e buscas de alto desempenho. A sua API opera de forma assíncrona, evitando o bloqueio da _thread_ principal do navegador.
        
          
        

### 2. Cookies HTTP

Cookies diferem fundamentalmente das APIs de Web Storage, pois foram projetados primordialmente para comunicação com o servidor, e não apenas para armazenamento local.

  

- **Definição Operacional:** Um cookie é um pequeno fragmento de dados gerado por um servidor web e enviado ao navegador do usuário. O navegador armazena este fragmento e, de forma automatizada, anexa esses dados no cabeçalho (_header_) HTTP de todas as requisições subsequentes direcionadas àquele mesmo servidor.
    
      
    
- **Propósito:** O protocolo HTTP é _stateless_ (não guarda estado das requisições anteriores). Os cookies existem para implementar o gerenciamento de estado, permitindo operações como autenticação de usuários (sessões) e rastreamento.
    
      
    
- **Diretivas de Segurança (Atributos):**
    
      
    - **HttpOnly:** Quando esta diretiva é definida pelo servidor, o navegador proíbe que o cookie seja lido ou manipulado via JavaScript (por exemplo, via `document.cookie`). Isso mitiga o risco de roubo de sessão através da injeção de scripts maliciosos.
        
          
        
    - **Secure:** Exige que o cookie seja transmitido ao servidor exclusivamente por meio de conexões criptografadas (HTTPS).
        
          
        
    - **SameSite:** Controla o comportamento de envio do cookie em requisições de origem cruzada. O valor `Strict` impede o envio em qualquer requisição originada de outro site; o valor `Lax` permite o envio em navegações de nível superior seguras (como o clique em um link); o valor `None` permite o envio em todas as requisições, exigindo obrigatoriamente a presença da diretiva `Secure`.
        
          
        

### 3. Vulnerabilidades Clássicas de Segurança Front-End

Para compreender a escolha entre _localStorage_ e _cookies_ para armazenamento de credenciais (como tokens JWT), é imperativo dominar duas vulnerabilidades fundamentais:

  

- **XSS (Cross-Site Scripting):**
    
      
    - **Mecanismo:** Ocorre quando falhas de validação ou sanitização permitem que um atacante injete scripts executáveis (geralmente JavaScript) em uma página web legítima, sendo executados nos navegadores de outros usuários.
        
          
        
    - **Vetor de Ataque no Armazenamento:** Um script XSS tem acesso total ao objeto global `window`. Portanto, ele pode ler qualquer dado armazenado no _localStorage_ ou _sessionStorage_ e enviá-lo ao atacante. Cookies com a diretiva `HttpOnly` estão imunes a este vetor de leitura direta via JavaScript.
        
          
        
- **CSRF (Cross-Site Request Forgery):**
    
      
    - **Mecanismo:** Ocorre quando um usuário autenticado é induzido a executar ações indesejadas em uma aplicação web. O ataque explora o comportamento padrão do navegador de anexar cookies automaticamente em todas as requisições para o domínio alvo.
        
          
        
    - **Vetor de Ataque:** O atacante cria um site malicioso que faz uma requisição HTTP forjada (por exemplo, uma transferência bancária) para o domínio onde a vítima já possui um cookie de sessão válido. O servidor processa a requisição por considerar o cookie legítimo. A configuração do atributo `SameSite` nos cookies é a principal defesa contemporânea contra o CSRF.
        
          
        

### 4. CORS (Cross-Origin Resource Sharing)

O CORS é um conceito que causa extrema confusão entre desenvolvedores por incompreensão da política de segurança subjacente.

  

- **Same-Origin Policy (Política de Mesma Origem):**
    
      
    - **Definição:** É uma diretriz de segurança estrutural dos navegadores. Ela determina que um documento ou script carregado de uma Origem "A" não pode interagir livremente com recursos pertencentes a uma Origem "B".
        
          
        
    - **Definição Formal de Origem:** Uma Origem é a combinação exata de três elementos: o Protocolo (ex: `https://`), o Domínio (ex: `api.exemplo.com`) e a Porta (ex: `443`). Qualquer alteração em um destes três elementos caracteriza uma origem diferente.
        
          
        
- **Mecanismo do CORS:**
    
      
    - **Definição:** O Compartilhamento de Recursos de Origem Cruzada (CORS) é um sistema baseado em cabeçalhos HTTP estendidos que permite a um servidor declarar explicitamente quais outras origens têm permissão para acessar os seus recursos, relaxando as restrições da Política de Mesma Origem.
        
          
        
    - **Preflight Request (Requisição de Pré-voo):** Para requisições HTTP que podem modificar os dados no servidor (métodos como POST, PUT, DELETE, ou requisições contendo cabeçalhos personalizados), o navegador não envia a requisição principal imediatamente. Primeiro, ele emite automaticamente uma requisição com o método HTTP `OPTIONS`. O servidor responde informando os métodos e origens permitidos. Se a origem atual for aceita pelo servidor, o navegador procede com a requisição principal; caso contrário, o navegador bloqueia a requisição e lança o erro de CORS visível no console.
